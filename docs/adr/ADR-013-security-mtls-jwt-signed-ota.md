# ADR-013: Security: mTLS, JWT, Signed OTA, Fail-Safe

## Status
Accepted

## Context
The robot moves physically and is network-connected (WiFi/Ethernet). Threats include: rogue MQTT clients issuing motion commands, tampered firmware over the air, unauthorized API access from the LAN, and - independent of attackers - hardware/software faults causing dangerous motion. Security must be designed-in, not appended.

## Decision
Four security pillars, all mandatory:

1. **mTLS everywhere on the mesh**: private CA; per-node certificates (RPi + each ESP32); MQTT listener on 8883 requires client certificates; ACL restricts per-node topic rights. Certificates generated by `docker/certs/generate.sh`, secrets via `docker/secrets/`.
2. **JWT (RS256) for REST API + WebSocket**: authenticated, rate-limited commands; Swagger UI behind auth.
3. **Signed OTA**: ECDSA P-256 per ADR-011.
4. **Fail-safe behavior independent of security layer**: on any fault or loss of comms - servos → home, motors → brake, LED → error pattern; hardwired E-stop on motor nodes; software watchdogs.

Additional rules:
- Input validation at every trust boundary (REST handler, gateway subscriber, firmware command parser): range checks, rate limits.
- No secrets in the repository or in logs.

```
CA ──▶ Node Certificates ──▶ MQTT mTLS (all 6 nodes)
   ├──▶ JWT signing ──▶ REST/WS auth
   └──▶ OTA signing key (ECDSA)
```

## Alternatives Considered
1. **Plain MQTT + password auth** - Rejected: credentials leakable; no node identity; spoofing trivial on WiFi.
2. **VPN-only perimeter security** - Rejected: defense in depth required once a device is compromised; robot must stay safe inside its own network.
3. **OAuth/OIDC external IdP** - Deferred: adds cloud dependency; local-first constraint wins for v1.

## Consequences
**Positive:**
- Every command is attributable to an authenticated identity (audit trail).
- Compromised ESP32 cannot forge other nodes' identities (unique certs).
- Safety does not depend on the security stack working correctly.

**Negative:**
- Certificate lifecycle (generation, distribution, renewal) is operational burden - renewal automation planned in ROADMAP v0.4.0.
- Debugging message flows requires TLS tooling setup.

## Implementation Notes
- Mosquitto configured with TLS listener + acl_file (`docker/config/mosquitto/`); container uid/gid aligned with host cert permissions during stabilization session (git history 2026-08-13).
- Healthcheck reads only anonymous-permitted `$SYS` topics.
- Open items: automatic certificate renewal; JWT issuance flow in REST layer to be finalized with CI work (v0.3.0).
